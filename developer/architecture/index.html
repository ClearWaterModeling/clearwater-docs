    v2 Architecture Walkthrough¶

    This page describes the ClearWater v2 architecture that the ongoing refactor is building toward. The v2 architecture replaces the implicit variable-graph model used in v1 with an explicit Process abstract base class, a shared VariableRegistry, and optional chunked-zarr storage for memory-efficient long simulations. New contributors should read this page before adding code to clearwater_modules_v2/.

    Three-Package Layout¶

    ClearWater is distributed as three cooperating Python packages. Each package owns a distinct concern, and the dependency arrows flow in one direction only.

    Package Responsibility Depends on
    ClearWater-Data Variable registry, data sources, chunked zarr storage, array type aliases None within the project
    ClearWater-Modules Water quality kinetics; the Process ABC, Model orchestrator, and individual processes (temperature, algae, nitrogen, etc.) ClearWater-Data
    ClearWater-Riverine 2D hydraulic transport on unstructured meshes; couples hydraulics to the water quality modules ClearWater-Data, ClearWater-Modules

    ClearWater-Data defines the shared primitives (VariableRegistry, DataSource, ChunkedDataSource, ChunkedZarrDataStore, the ArrayLike type alias). ClearWater-Modules builds the kinetic processes on top of those primitives. ClearWater-Riverine supplies the transport layer and orchestrates coupled hydraulic and water quality simulations.

    Overall Data Flow¶

    flowchart LR
    Config[YAML config] --> Factory[ProcessFactory]
    Factory --> Model
    DataSources[DataSource and<br/>ChunkedDataSource] --> Registry[VariableRegistry]
    Model --> Registry
    Registry --> P1[Process: Temperature]
    Registry --> P2[Process: FloatingAlgae]
    Registry --> P3[Process: Nitrogen]
    P1 --> Registry
    P2 --> Registry
    P3 --> Registry
    Registry --> Output[ChunkedZarrDataStore]

    The Model class reads a YAML configuration, assembles the configured processes via ProcessFactory, loads input data into the VariableRegistry, steps through time calling each Process.run(time, registry) in order, and writes the selected output variables to a zarr store.

    The Process Abstract Base Class¶

    Every water quality process is a subclass of Process defined in clearwater_modules_v2/processes/base.py. The base class specifies a three-phase lifecycle.

    from abc import ABC, abstractmethod
from datetime import datetime, timedelta
from clearwater_data.variables import VariableRegistry


class Process(ABC):
    variables: list[str] = []
    time_step_seconds: int

    def __init__(self, time_step: timedelta) -> None:
        self.time_step = time_step
        self.time_step_seconds = self.time_step.total_seconds()

    @classmethod
    def from_config(cls, config: dict, variable_registry: VariableRegistry) -> "Process":
        return cls(**config)

    def init_process(self, model: "Model", registry: VariableRegistry) -> None:
        """One-time setup before the time loop begins."""
        pass

    def validate(self, registry: VariableRegistry) -> None:
        for variable in self.variables:
            if variable not in registry:
                raise ValueError(f"Variable {variable} not registered for process.")

    def finalize_process(self, model: "Model", registry: VariableRegistry) -> None:
        """Cleanup hook called after the time loop (or each chunk)."""
        return None

    @abstractmethod
    def run(self, time: datetime, registry: VariableRegistry) -> None:
        """Advance the process state one time step."""
        raise NotImplementedError

    The three lifecycle hooks are:

    1. init_process(model, registry) is called once before the time loop begins. The hook inspects the model for coupling partners (for example, model.has_process("FloatingAlgae")) and sets per-process flags that control which source and sink terms are active.
    2. run(time, registry) advances the process one time step. The method pulls inputs from the registry via registry.get_at_time(var, time), computes the derivative, integrates forward, and writes the result back via registry.set_at_time(var, value, time).
    3. finalize_process(model, registry) is called after the time loop completes. In chunked mode, the Model calls finalize_process at the end of each chunk, which gives processes a hook to flush state or record diagnostics.

    The variables class attribute names every registry key the process reads or writes. The validate method checks that every listed variable is present in the registry before the simulation starts.

    The VariableRegistry¶

    The VariableRegistry, defined in ClearWater-Data, is the single source of truth for simulation state. Processes never pass state to one another directly. Instead, each process reads inputs from the registry and writes outputs to the registry.

    The registry exposes time-indexed accessors so that processes with different time steps can read consistent snapshots:

    # Read the current-time value of a variable
water_temperature = registry.get_at_time("water_temperature", time)

# Write an updated value at the current time
registry.set_at_time("water_temperature", new_water_temperature, time)

    Because state lives in the registry, inter-process coupling is explicit and traceable. For example, the nitrogen process reaches the floating algae process via model.get_process("FloatingAlgae") to read the algal respiration rate, then computes the ammonium source term from that rate and writes the updated ammonium concentration back to the registry.

    Always persist state

    A Process.run method that computes an updated value but does not call registry.set_at_time silently drops the update. This is a known pitfall in early v2 work. Every run method must end with set_at_time calls for every state variable it updates.

    The Model Orchestrator¶

    The Model class in clearwater_modules_v2/model.py owns the time loop. At construction time the Model receives:

    • A tuple of Process instances, in the order they should run each step.
    • A VariableRegistry.
    • A dictionary mapping variable names to DataSource or ChunkedDataSource objects.
    • Simulation bounds (start_time, end_time, time_step).
    • The list of output variable names to persist.
    • An optional chunk_size, which switches the model into chunked mode.

    The simplified time loop for a non-chunked run is:

    def run(self) -> None:
    if not self.__init_complete:
        self.__init_model()
    current_time = self.__start_time
    while current_time < self.__end_time:
        current_time_seconds = current_time.timestamp()
        for process in self.__processes:
            if current_time_seconds % process.time_step_seconds == 0:
                process.run(current_time, self.__registry)
        current_time += self.__time_step
    self.__save_output_model(self.__start_time, self.__end_time)

    The modulo check on time_step_seconds allows processes with different cadences to coexist. A process with a 15-minute time step advances only on time stamps that are multiples of 900 seconds; a process with a 5-minute time step advances every 300 seconds.

    Two helper methods on Model support inter-process coupling:

    if model.has_process("FloatingAlgae"):
    algae = model.get_process("FloatingAlgae")
    respiration = algae.rate_respiration(...)

    Processes call these helpers from init_process to detect optional couplings and from run to pull source or sink terms from sibling processes.

    ProcessFactory and YAML Assembly¶

    The ProcessFactory, also in base.py, is a registry of Process constructors keyed by short names. Each Process subclass registers itself by decorating its from_config classmethod:

    class FloatingAlgae(Process):
    @ProcessFactory.register("floating_algae")
    @staticmethod
    def from_config(config: dict, variable_registry: VariableRegistry) -> "FloatingAlgae":
        return FloatingAlgae(**config)

    The YAML configuration lists the processes to run along with their kinetic parameters:

    processes:
  - name: temperature
    config:
      wind_a: 0.3
      wind_b: 1.5
      wind_c: 1.0
      time_step: 300
  - name: floating_algae
    config:
      growth_rate_max: 2.5
      settling_velocity: 0.15
      time_step: 300

    At startup, the configuration loader calls ProcessFactory.from_config(name, config, registry) for each entry, which returns the constructed Process instance. The assembled tuple of processes is then passed to the Model along with the registry, data sources, and output settings.

    Chunked Versus Full Simulation Modes¶

    The Model supports two execution modes:

    • Full mode holds the entire simulation history in memory. The registry is populated once from all data sources, the time loop advances, and the output is written at the end.
    • Chunked mode streams through the simulation in time-chunked windows. On each chunk boundary the Model reads the next chunk from any ChunkedDataSource objects, runs the inner time loop over the chunk, writes the chunk's output to the ChunkedZarrDataStore, and calls finalize_process on each Process.

    Chunked mode is what makes long simulations feasible on machines with limited memory. A full-year hourly simulation on a fine mesh does not fit in RAM; a chunked run with a one-week chunk size does.

    When to choose which mode

    Use full mode for short development runs and for debugging. Use chunked mode for production runs, for any simulation longer than a few days on a non-trivial mesh, and whenever output must be streamed rather than accumulated.
