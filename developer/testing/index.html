    Testing Strategy¶

    ClearWater uses pytest for all automated testing. Tests are organized into three layers that address different risks: unit tests confirm that individual rate methods are numerically correct, v1-parity tests confirm that the v2 refactor reproduces the v1 reference implementation, and integration tests confirm that the coupled model runs end-to-end and produces plausible output.

    New contributors should add tests in all three layers when they add a new Process subclass. The sections below describe what each layer is responsible for, where the tests live, and how to run them.

    Unit Tests¶

    Unit tests exercise a single method of a single class with synthetic inputs. They live under tests/unit/<process>/ and are the fastest feedback loop during development.

    For a new Process subclass, add a unit test for each public rate_* method. Each test should construct the process with explicit kinetic parameters, call the rate method with known inputs, and compare against a value computed by hand or from the closed-form expression.

    # tests/unit/tracer/test_rate_decay.py
from datetime import timedelta

import numpy as np
import xarray as xr

from clearwater_modules_v2.processes.tracer import Tracer


def test_rate_decay_scales_with_concentration():
    """Decay rate scales linearly with concentration at fixed temperature."""
    process = Tracer(
        time_step=timedelta(minutes=5),
        decay_rate_20=0.1,
        decay_theta=1.047,
    )
    tracer = xr.DataArray(np.array([1.0, 2.0, 4.0]))
    temperature = xr.DataArray(np.array([20.0, 20.0, 20.0]))

    rate = process.rate_decay(tracer, temperature)

    np.testing.assert_allclose(rate.values, [0.1, 0.2, 0.4])

    Unit tests should not depend on a running Model and should not read files from disk. Use small, fixed-size xarray DataArray inputs that make the expected output calculable by hand.

    v1-Parity Tests¶

    v1-parity tests are the linchpin of the v1-to-v2 refactor. Each test runs identical inputs through the v1 reference implementation and the corresponding v2 Process subclass, then asserts the outputs match within a documented tolerance. These tests live under tests/ with a test_*_calculations_v2.py naming convention. The existing tests/test_5_tsm_calculations_v2.py is the canonical template.

    A parity test should cover at least:

    1. A representative scalar case (single cell, constant forcing).
    2. A vectorized case (multiple cells with varying forcing).
    3. Boundary conditions, especially temperatures near 20 degrees Celsius where the Arrhenius correction is zero, and zero-concentration inputs.

    Tolerance selection matters. Pick the loosest tolerance that still detects real regressions. The project uses np.testing.assert_allclose with an explicit rtol. A relative tolerance of 1e-6 is typical for variables whose v1 implementation is free of known bugs. Document the tolerance in the test docstring along with the reason.

    def test_tracer_v1_parity_vectorized():
    """v2 Tracer matches v1 within 1e-6 relative tolerance on a 3-cell grid.

    Tolerance chosen to detect any change in the Arrhenius exponent while
    allowing for minor floating-point reordering between the two
    implementations.
    """
    # ... fixture setup ...
    np.testing.assert_allclose(v2_rate.values, v1_rate, rtol=1e-6)

    Beware of v1 bugs

    When the v1 implementation carries a known bug (for example, sentinel values in the NSM1 constants.py that cause Arrhenius blow-up at high temperatures), a strict parity target is neither possible nor desired. Document the divergence, pick a tolerance that captures the intended behavior, and reference the investigation note in the test docstring.

    Integration Tests¶

    Integration tests run a full coupled simulation end-to-end. They confirm that the Model loads input data, steps through time, calls every process in the configured order, and writes output to the zarr store without raising. They live under tests/integration/.

    Integration tests are slower than unit tests and should use a small reference mesh and a short simulation window. Assert on high-level outputs: that the zarr store contains every requested output variable, that the time axis matches the requested simulation window, and that the output values are finite and non-degenerate.

    def test_coupled_run_writes_expected_outputs(tmp_path):
    """Coupled Temperature + FloatingAlgae run writes both outputs to zarr."""
    model = build_test_model(root_directory=tmp_path)
    model.run()

    store = xr.open_zarr(tmp_path / "model_outputs.zarr")
    assert "water_temperature" in store
    assert "algae_floating" in store
    assert np.all(np.isfinite(store["water_temperature"].values))

    Running Tests Locally¶

    Run the full suite from the repository root.

    pytest tests/

    Run a single layer, a single file, or a single test.

    pytest tests/unit/                                   # all unit tests
pytest tests/test_5_tsm_calculations_v2.py           # one file
pytest tests/unit/tracer/test_rate_decay.py::test_rate_decay_scales_with_concentration

    Generate a coverage report.

    pytest --cov=clearwater_modules_v2 --cov-report=term-missing tests/

    Run tests in parallel on multi-core machines, which significantly speeds up the parity suite.

    pytest -n auto tests/

    Continuous Integration Expectations¶

    Every pull request must pass the full test suite in CI before it can be merged. The CI workflow:

    1. Checks out the branch and installs dependencies via pixi.
    2. Runs pytest tests/ with coverage.
    3. Fails the build if any test fails, if overall coverage drops below the configured threshold, or if new code lacks tests.

    Pull requests that add a new Process subclass without at least a unit test and a v1-parity test will be sent back for revision. See the Contributing Guidelines for the complete pull request checklist.

    Run the suite before pushing

    Running pytest tests/ locally before pushing catches most CI failures up front. The full suite on a laptop takes under a minute for unit tests and a few minutes for the integration layer.
