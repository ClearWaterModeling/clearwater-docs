    Chunked Zarr Data Store¶

    The ChunkedZarrDataStore is the disk-backed storage backend for ClearWater-Data. It persists every registered variable as a chunked zarr array, which allows ClearWater to run simulations whose full state history does not fit in memory and to produce output that is readable by any tool in the xarray / zarr ecosystem.

    When to Use the Zarr Backend¶

    Choose the zarr backend when one or more of the following conditions hold:

    • The simulation grid times the number of time steps exceeds available RAM.
    • Output must persist on disk for post-processing, visualization, or restart.
    • Multiple downstream tools (Jupyter notebooks, Dask workflows, external viewers) need random-access reads of the output.
    • Simulations run long enough that intermediate crashes would otherwise lose all results.

    For short simulations, unit tests, or single-cell scenarios, the default in-memory backend is simpler.

    Storage Layout¶

    Each registered variable becomes a zarr array under the store's root directory. The array dimensions match the variable's registered dimensions. Attributes such as units and long names are preserved in the zarr metadata.

    A typical on-disk layout for a 2D simulation with state variables T_water and NH4 and forcing variable T_air looks like:

    sim_output.zarr/
    T_water/
        .zarray
        .zattrs
        0.0, 0.1, ... (chunk files)
    NH4/
        ...
    T_air/
        ...
    .zgroup
    .zattrs

    Chunking Strategy¶

    Chunks are the fundamental unit of I/O in zarr. Choosing chunk sizes well is the single most important tuning decision for the zarr backend.

    General guidelines:

    • Align chunks with access patterns. ClearWater modules read and write one time slice per step across all cells. A chunk shape such as {"time": 24, "cell": N_cells} (one-day time chunks across the whole grid) works well when access is time-step-sequential.
    • Target 1--100 MB per chunk. Very small chunks generate excessive metadata overhead; very large chunks force loading more than needed.
    • Match chunk boundaries to analysis needs. If downstream analysis aggregates by day or by region, align the chunk boundaries so aggregations touch the minimum number of chunks.

    Specify chunks when constructing the store:

    from clearwater_data import ChunkedZarrDataStore

store = ChunkedZarrDataStore(
    path="./sim_output.zarr",
    chunks={"time": 24, "cell": 10000},
)

    Memory Footprint¶

    The zarr backend holds only the active chunks in memory. When a module requests a time slice, the store loads the chunk containing that slice, returns a view, and releases the chunk when it is no longer referenced. Peak memory usage is therefore approximately:

    \[ \text{Peak RAM} \approx \sum_{\text{variables}} \text{(chunk size)} \times \text{(active chunks per variable)} \]

    For a grid of 100,000 cells, 8-byte floats, and a chunk shape of {"time": 24, "cell": 10000}, each chunk is \(24 \times 10{,}000 \times 8 = 1.9\) MB. A registry with 15 state variables touches roughly 30 MB when a single time slice is active, independent of the total number of time steps.

    Opening, Appending, and Reading¶

    Create a new store by passing a path that does not yet exist. Re-open an existing store by passing the same path; the store detects the existing zarr group and attaches to it. Reads can proceed from any tool that understands zarr:

    import xarray as xr

ds = xr.open_zarr("./sim_output.zarr")
print(ds)
T = ds["T_water"].sel(time=slice("2024-01-01", "2024-01-31"))

    Closing the Store¶

    Call store.close() (or registry.close() if you are working through the registry) when the simulation completes. This flushes any pending writes and finalizes the zarr metadata. Most zarr operations are write-through, so data loss from an unexpected crash is typically limited to the currently buffered chunk.

    Performance Tips¶

    • Write one full time slice per step rather than many small per-cell writes. The chunking strategy assumes contiguous spatial writes.
    • If the simulation is embarrassingly parallel across cells, ensure that parallel workers write to disjoint chunk regions to avoid contention.
    • For long simulations, periodically verify disk usage; zarr produces one small file per chunk, and file-system inode limits can become the binding constraint before disk space does.
